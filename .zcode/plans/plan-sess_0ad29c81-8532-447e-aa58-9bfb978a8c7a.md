# Fluent Mailbox: Multi-Provider + Multi-Mailbox Architecture

**Goal:** Replace the hard-wired AWS dependency with a driver system so any WordPress admin can connect mailboxes they already own (cPanel/hosting email, Zoho, Gmail) via **IMAP/SMTP**, keep **AWS SES** as an optional driver, add **API providers** (Mailgun, Postmark) — and support **multiple mailboxes** (marketing@ / business@ / support@) each with its own connection.

**Deferred (later phase):** Gmail/Microsoft OAuth2 (Microsoft has disabled basic-auth IMAP entirely; Google Workspace OAuth needs a verified developer app — both are a separate, larger build).

**Decided:** minimum PHP is **8.0** (`webklex/php-imap ^5.5` requires `^8.0.2`; `composer.json` already says `>=8.0`). This drops 7.4 installs — add `Requires PHP: 8.0` (and `Requires at least`) to the plugin header in `fluent-mailbox.php` so WordPress refuses activation on older PHP instead of fataling.

## Phase 1 — Driver abstraction (backend core) ✅

1. **`app/Services/Contracts/MailDriverInterface.php`** — interface with:
   - `testConnection(): bool|WP_Error`
   - `send(array $args): string|WP_Error` (args: to, subject, html body, cc, bcc, attachment file paths; returns provider message-id)
   - `fetchNewEmails(object $mailbox): int|WP_Error` (pull-based inbound)
2. **`app/Services/DriverManager.php`** — registry/factory:
   - Built-in drivers: `imap`, `ses`, `mailgun`, `postmark`
   - `make($mailbox): MailDriverInterface` — instantiates driver with the mailbox's settings
   - `drivers(): array` — driver metadata + settings field schemas (consumed by frontend forms)
   - `apply_filters('fluent_mailbox_drivers', ...)` so third parties can register drivers
3. **`app/Models/Mailbox.php`** — new model (mirrors existing `Email`/`Tag` static `$wpdb` pattern).

## Phase 2 — Database: mailboxes table + mailbox dimension ✅ (incl. 4b)

4. **`app/Common/DatabaseMigration.php`**:
   - New table `wp_fluent_mailbox_mailboxes`: `id, name, email, from_name, driver, driver_settings (JSON longtext), category (marketing|business|support|other), color, is_active, is_default, last_synced_at, sync_state (JSON longtext, for IMAP UID tracking), created_at, updated_at`
   - Add `mailbox_id` column + index to `wp_fluent_mailbox_emails` (via existing `addMissingColumns()`); bump `fluent_mailbox_db_version`
   - **Legacy migration:** if old AWS options (`fluent_mailbox_aws_key` + `fluent_mailbox_from_email`) exist and no mailbox rows do, auto-create a default SES mailbox from them so existing installs keep working unchanged

4b. ✅ **Per-mailbox de-duplication (ADJUSTMENT — real bug):** `InboundService::processFromContent()` currently dedups on `message_id` alone (`InboundService.php:48`). With multiple mailboxes, a message CC'd to `marketing@` and `support@` arrives through both connections with the *same* `Message-ID`, and the second copy is silently dropped — one mailbox never sees it.
   - Change the duplicate check to `WHERE message_id = %s AND mailbox_id = %d`
   - Add composite index `KEY message_mailbox (message_id, mailbox_id)` via `addMissingColumns()`/index check, same pattern as the `mailbox_id` index
   - IMAP driver's `imap_{mailbox}_{uid}` fallback IDs are already mailbox-scoped; keep that

## Phase 3 — IMAP/SMTP driver (the universal one) ✅

5. **Composer:** `webklex/php-imap ^5.5` (pure PHP, no `ext-imap` host requirement; requires PHP ^8.0.2 — see "Decided" above) + `zbateson/mail-mime-parser ^3.0`. No new SDK for sending: reuse **PHPMailer bundled with WP core** (`wp-includes/PHPMailer`).
6. **`app/Services/Drivers/ImapSmtpDriver.php`**:

## Phase 4 — SES driver (refactor existing code, no behavior change) ✅ (+ item 7 cleanup)

7. **`app/Services/Drivers/SesDriver.php`** — wraps existing `SesService::sendEmail()` and `InboundService::processFromS3()/fetchNewEmails()`, reading config from `mailbox->driver_settings`. `AwsSetupService` inbound provisioning (S3/SNS/rule) stays as-is, invoked from the mailbox setup flow.
   - **ADJUSTMENT — single source of truth:** today SES config lives in three places: `SesDriver` falls back to `wp_options` (`SesDriver.php:88-92`), `SettingsController::saveConnection()` still writes `wp_options`, and `is_configured` reads `wp_options`. Rule going forward: the legacy `fluent_mailbox_aws_*` / `fluent_mailbox_from_*` options are **read only by the migration** in `DatabaseMigration::migrateLegacyAwsMailbox()`, which copies them into the mailbox's `driver_settings`. After that, the `SesDriver` runtime fallback is removed, the AWS wizard writes to the mailbox row (item 20), and `is_configured` uses `Mailbox::hasActive()` (item 15). Optionally delete the old options once the migrated mailbox exists.

## Phase 5 — API provider drivers ✅ (incl. adjustments 8/10)

8. **`app/Services/Drivers/MailgunDriver.php`** — send via `wp_remote_post` to `api.mailgun.net/v3/{domain}/messages` (multipart for attachments, no SDK); inbound via Mailgun Routes → webhook, **verify HMAC-SHA256 signature** (timestamp+token, signing key).
   - ✅ **ADJUSTMENT — ingest raw MIME:** `handleWebhook()` currently rebuilds a fake MIME from `from`/`subject`/`body-html`, so attachments, CC and original headers are lost. Configure the Mailgun Route to forward to the webhook URL ending in `/mime` so Mailgun posts the full message in `body-mime`, and pass that straight to `processFromContent()` — same path as Postmark and IMAP. Attachments then flow through the existing attachment handling.
   - ✅ **ADJUSTMENT — no signing-key brute force:** verify against the single mailbox identified by the URL (item 10) instead of looping every Mailgun mailbox; `recipient` may still override routing via `Mailbox::routeInbound()`.
9. **`app/Services/Drivers/PostmarkDriver.php`** — send via `api.postmarkapp.com/email` (`X-Postmark-Server-Token` header); inbound via Postmark inbound webhook which posts the raw MIME directly. Already uses per-mailbox `inbound_secret`; move `mailbox`/`secret` from query params to the route shape in item 10.
10. ✅ **Webhook routes (ADJUSTMENT — one scheme for every driver):** public `POST /webhook/{driver}/{mailbox_id}?secret={inbound_secret}` registered in `Router.php` with `permission_callback => __return_true`, dispatching to `DriverManager::make($mailbox)->handleWebhook($request)`.
    - Mailbox is resolved from the URL, `secret` is checked with `hash_equals()` against `driver_settings.inbound_secret` **before** any provider-specific verification (Mailgun HMAC, SNS message validation) — O(1), no per-driver URL conventions
    - `inbound_secret` is auto-generated (`wp_generate_password(32, false)`) when a mailbox is created; the full webhook URL is shown in the mailbox edit form
    - The existing SNS `/webhook` stays for backward compatibility with already-provisioned SES subscriptions — **cannot require a secret without breaking them** (their subscribed URL carries none); instead its unauthenticated direct-post branch (arbitrary inbox-row creation) was removed. Retire the endpoint once the mailbox setup flow (6b/item 20) re-subscribes SNS to `/webhook/ses/{id}?secret=…`
    - Add `handleWebhook(WP_REST_Request): WP_REST_Response|WP_Error` to `MailDriverInterface` (default no-op for polling-only drivers)

## Hardening (folded in)

- Every public webhook endpoint verifies a per-mailbox `inbound_secret` from the URL first, then the provider's own signature (Mailgun HMAC, SNS signature/topic check) — the current SNS `/webhook` accepts unauthenticated posts and must get the same check
- Store driver secrets in `driver_settings` with the same treatment as current AWS options (wp_options); document the risk
- Never return raw secrets from `GET /mailboxes`; mask like `SettingsController::mask()`
